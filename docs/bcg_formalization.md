# BCG Formalization
## Three Candidate Formulations — Formal Comparison and Recommendation

---

## BACKGROUND

The Behavioral Contract Graph (BCG) must serve as a formal intermediate representation. It must be:
- Expressive enough to capture temporal, resource, and control-flow contracts
- Computationally tractable for queries (contract retrieval, impact analysis)
- Compatible with both static analysis output and dynamic trace observations
- Provenance-aware at the per-contract level
- Capable of representing uncertainty and conflict

Three candidate formulations are evaluated below. We do NOT select the one that sounds most impressive. We select the one that best satisfies the requirements.

---

## FORMULATION F-I: Labeled Attributed Multi-Graph (LAMG)

### Definition

```
BCG_I = (V, E, C, P, D, Γ)
```

Where:
- **V** = finite set of typed vertices (entities), each v ∈ V has type τ(v) ∈ EntityType and attribute map α(v): Attr → Val
- **E** = finite set of labeled directed edges (structural relationships), each e ∈ E has label λ(e) ∈ RelType and attribute map
- **C** = finite set of behavioral contracts, each c ∈ C is a tuple (id, type, subject, predicate, object, scope, precond, confidence)
- **P** = provenance map P: C → ProvenanceRecord where ProvenanceRecord = {source_artifact, location, extraction_method, model, timestamp}
- **D** = dynamic observation set D ⊆ ExecutionEvent where ExecutionEvent = {event_id, timestamp, artifact_id, operation, resource, predecessor, successor, return_code}
- **Γ** = validation map Γ: C → ValidationState × ConfidenceVector

**Semantics of C:** Each contract c = (id, type, subj, pred, obj, scope, precond, conf) specifies that within any execution satisfying scope and precond, the relationship pred(subj, obj) must hold. pred is drawn from {PRECEDES, PRODUCES_BEFORE_CONSUMES, REQUIRES_STATE, MUST_NOT_FOLLOW_ON_ERROR}.

### Expressive power
- Captures all three Paper-1 contract types (temporal, resource, control)
- Separate C set allows contracts independent of structural edges
- D set links to execution events independently of C

### Ambiguity
- C and E can overlap semantically (a CALLS edge vs. a control-flow contract). Requires discipline to avoid duplication.
- Preconditions in contracts are informal unless formalized.

### Computational complexity
- Contract retrieval: O(|C|) linear scan or O(log|C|) with index
- Impact analysis: O(|V| + |E|) BFS/DFS on structural graph
- Reconciliation: O(|C| × |D|) in worst case, reducible with hash indexing

### Queryability
- Standard graph query languages (Cypher, SPARQL-like) apply to (V, E)
- C requires separate relational query
- D requires timeline queries

### Provenance support
- ✓ Full per-contract provenance via P map

### Dynamic evidence support
- ✓ D is a first-class component
- ✓ Γ stores per-contract validation state after reconciliation with D

### Suitability for modernization analysis
- ✓ Contract diff C_original − C_modernized is straightforward set operation
- ✓ Impact analysis via structural graph (V, E)

### Static analysis compatibility
- ✓ V and E populated directly from static extraction

### Execution trace compatibility
- ✓ D populated from normalized trace adapter output
- ✓ Γ updated after reconciliation pass

**RATING: Strong candidate. Main weakness: C/E overlap requires explicit management.**

## FORMULATION F-II: Temporal Logic Contract Hypergraph (TLCH)

### Definition

```
BCG_II = (V, H, φ, P, D)
```

Where:
- **V** = entities (same as F-I)
- **H** = hyperedges connecting sets of vertices (supporting n-ary relationships)
- **φ** = formula map φ: H → LTL-formula, mapping each hyperedge to a formal temporal logic specification
- **P** = provenance (same as F-I)
- **D** = dynamic observations (same as F-I)

**Semantics:** Each hyperedge h ∈ H is associated with a temporal formula φ(h) over the execution alphabet Σ = {events generated by entities in V}. The formula is evaluated against execution traces to determine satisfaction.

Example:
```
φ(h_JA_JB) = □(consume(JB, FILE_X) → ◇[0,∞](produce(JA, FILE_X) ∧ t_produce < t_consume))
```

### Expressive power
- ✓✓ Highly expressive — LTL can express complex temporal obligations
- ✓ Hyperedges support multi-party contracts (e.g., "JOB-A, JOB-B, and JOB-C must complete before JOB-D")
- ✓ Formally decidable satisfaction check against finite traces

### Ambiguity
- ✓ Low ambiguity — formal semantics of LTL are well-defined
- ✗ Writing LTL formulas for all contracts requires expertise
- ✗ Automatically generating LTL from source is hard — requires careful formula template library

### Computational complexity
- Model checking LTL against finite traces: O(|trace| × |φ|) per formula
- For a system with |C| contracts and |D| trace events: O(|C| × |D|) worst case
- For large trace sets this becomes expensive

### Queryability
- ✗ LTL formulas are not natively queryable as graph structures
- ✗ Integrating with graph databases is non-trivial
- ✓ Model checkers (SPIN, NuSMV) can check φ against D

### Provenance support
- ✓ Per-hyperedge provenance is feasible
- ✗ More complex to implement than F-I

### Dynamic evidence support
- ✓✓ Strong — LTL model checking directly validates φ against traces
- ✓ Can distinguish satisfied/violated/unobserved formulas

### Suitability for modernization analysis
- ✓ Contract diff is formula set diff
- ✗ Comparing LTL formulas for semantic equivalence is PSPACE-complete — expensive
- ✗ Counterfactual analysis harder (cannot easily "restore" an LTL formula)

### Verdict
Theoretically elegant but impractical for the Paper 1 scope. LTL model checking on batch execution traces would require significant infrastructure not justified by the research questions. The expressive power exceeds what is needed for temporal/resource/control contracts in JCL+COBOL.

**RATING: Theoretically strongest; practically overkill for Paper 1. Reserve for future work.**

## FORMULATION F-III: Relational Contract Database with Graph View (RCDG)

### Definition

```
BCG_III = {Entities, Relations, Contracts, Evidence, Provenance}
```

Where each component is a normalized relational schema:

```sql
Entities(entity_id PK, entity_type, artifact_id, name, location, metadata JSON)
Relations(rel_id PK, rel_type, source_entity FK, target_entity FK, confidence, metadata JSON)
Contracts(contract_id PK, contract_type, subject_entity FK, predicate, object_entity FK,
          scope, preconditions, formal_statement TEXT, natural_language TEXT,
          confidence FLOAT, validation_state, created_at)
Evidence(evidence_id PK, contract_id FK, evidence_type, source_artifact, source_location,
         extraction_method, content TEXT, timestamp)
DynamicObservations(obs_id PK, event_id, timestamp, artifact_id FK, operation, resource,
                    predecessor_obs_id FK, successor_obs_id FK, return_code, metadata JSON)
ContractObservationLinks(contract_id FK, obs_id FK, support_type)
```

The "graph" view is a materialized projection over this schema.

### Expressive power
- ✓ Sufficient for Paper 1 contracts
- ✗ Cannot express complex multi-party temporal formulas without extension
- ✓ Easy to extend schema for new contract types

### Ambiguity
- ✓ Low — relational schema enforces type discipline
- ✓ Formal statement column allows optional formal specification

### Computational complexity
- SQL queries with proper indexing: O(log n) for most contract retrieval
- Impact analysis requires recursive CTE or graph query extension
- ✓ Most efficient for large datasets

### Queryability
- ✓✓ Excellent — standard SQL works for all contract queries
- ✓ Graph databases (Neo4j) can be used as storage backend
- ✓ Easy to serialize to JSON for UI

### Provenance support
- ✓✓ Excellent — Evidence table directly supports per-contract provenance
- ✓ Multiple evidence rows per contract naturally supported

### Dynamic evidence support
- ✓ DynamicObservations table stores normalized events
- ✓ ContractObservationLinks maps observations to contracts
- ✗ Timeline queries less natural than in F-I or F-II

### Suitability for modernization analysis
- ✓ Contract diff is straightforward set query
- ✓ Impact analysis possible with graph projection
- ✓ Easy to implement counterfactual: diff two contract sets

### Verdict
Most implementable. Excellent for querying, provenance, and evidence management. Lacks the formal elegance of F-II but avoids its complexity. Close to F-I but structured relationally.

**RATING: Most practical; excellent queryability; best fit for Paper 1.**

## RECOMMENDED FORMULATION: F-I WITH RELATIONAL STORAGE BACKEND

### Rationale

The chosen design is a **hybrid**: the **conceptual model follows F-I** (typed vertices, labeled edges, separate contract set, provenance map, dynamic observation set, validation map) but the **physical storage follows F-III** (relational tables / graph database).

This gives:
- The formal clarity of F-I (named components with clear semantics)
- The queryability and provenance richness of F-III
- The ability to extend toward F-II formulas in future work (contracts have a `formal_statement` field)

### Formal Definition (Final)

```
BCG = (V, E, C, P, D, Γ)

V: Entity set
   v ∈ V ⟹ (id: UUID, type: EntityType, artifact: ArtifactRef, name: str, location: SourceLoc, attributes: Map)

E: Structural relationship set
   e ∈ E ⟹ (id: UUID, type: RelType, src: V, tgt: V, confidence: [0,1], attributes: Map)

C: Behavioral contract set
   c ∈ C ⟹ (id: UUID, type: ContractType, subject: V, predicate: Predicate, object: V,
              scope: Scope, preconditions: [Condition], formal: Formula|None,
              natural: str, confidence: ConfidenceVector)
   where ContractType ∈ {TEMPORAL, RESOURCE, CONTROL_FLOW, DATA, STATE, ERROR}
   and   Predicate ∈ {PRECEDES, PRODUCES_BEFORE_CONSUMES, REQUIRES_STATE, MUST_NOT_FOLLOW_ON_ERROR, ...}

P: Provenance map
   P: C → ProvenanceRecord
   ProvenanceRecord ⟹ (source_artifact: ArtifactRef, source_location: SourceLoc,
                        static_evidence: [Evidence], dynamic_evidence: [Evidence],
                        extraction_method: ExtractionMethod, model: str|None,
                        prompt_version: str|None, timestamp: datetime)
   ExtractionMethod ∈ {DETERMINISTIC, LLM, HUMAN, EXECUTION}

D: Dynamic observation set
   d ∈ D ⟹ (event_id: UUID, timestamp: datetime, execution_id: str, artifact_id: ArtifactRef,
              operation: OperationType, resource: ResourceRef, predecessor_events: [UUID],
              successor_events: [UUID], input: any, output: any, return_code: int|None, metadata: Map)

Γ: Validation metadata map
   Γ: C → (ValidationState, ConfidenceVector)
   ValidationState ∈ {STATIC_CANDIDATE, DYNAMICALLY_OBSERVED, STATIC_DYNAMIC_SUPPORTED,
                       STATIC_DYNAMIC_CONFLICT, HUMAN_VALIDATED, GROUND_TRUTH, UNRESOLVED, NOT_OBSERVED}
   ConfidenceVector ⟹ (static_support: [0,1], dynamic_support: [0,1], cross_artifact_support: [0,1],
                         provenance_quality: [0,1], human_validation: [0,1], execution_frequency: [0,1],
                         ambiguity_penalty: [0,1])
   aggregate_confidence(cv) = weighted_mean(cv, w) where w is defined in config/confidence_weights.yaml
   NOTE: aggregate_confidence is NOT a probability. It is a normalized evidence strength score.
```

### Why Not F-II?
LTL model checking is powerful but requires complete formula specification and model-checking infrastructure. For Paper 1's scope (JCL+COBOL temporal/resource/control contracts), the added complexity is not justified. The `formal` field in C allows future LTL formulas to be attached without redesigning the BCG.

### Why Not Pure F-III?
Pure relational representation obscures the graph structure that makes impact analysis and visualization natural. The conceptual model should remain graph-first; storage is an implementation detail.
