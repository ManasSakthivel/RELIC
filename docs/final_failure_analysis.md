## Failure: F-01 — Six Single-Step JCL Files Produce F1=0.0 (RQ1 Macro-F1 Dilution)

**Category:** BENCHMARK_DESIGN
**Cause:** 6 of 11 held-out JCL files contain exactly 1 job step. Per convention, a file with zero oracle contracts and zero system contracts scores precision=1.0, recall=0.0, F1=0.0. This is not an extractor error — it is a mathematical artifact of the macro-averaging convention applied to degenerate files.
**Evidence:** `results/rq1/rq1_independent.json` per_file section: CLOSEFIL (1 step), INTCALC (1 step), POSTTRAN (1 step), CICDBCMP (1 step), SORTTEST (1 step) + CICDBCMP all have oracle_contracts=0.
**Impact:** Macro-F1 = 0.5455 [CI: 0.2727, 0.8182] instead of ~0.8–0.9. The wide CI [0.27, 0.82] (55pp width) is directly caused by this bimodal distribution (6 files F1=0, 5 files F1=1).
**Fixable:** NO — the files are genuinely single-step. This is a real characteristic of the benchmark, not a flaw. The macro convention is standard; the alternative (exclude zero-contract files from macro average) would need explicit justification.
**Fixed:** DOCUMENTED in evidence_ledger.md (RQ1-03, RQ1-06) and FINAL_RESULTS.md.
**Residual Limitation:** Macro-F1 is not a reliable summary statistic for this benchmark. Paper must report both micro (1.000) and macro (0.5455) with CI and must explain why the bimodal distribution arises. Do not present either metric without the other.

## Failure: F-02 — Baseline-A Misses All SUPPRESS_RETURN_CODE_CHECK and ALTER_ERROR_BRANCH (RQ2)

**Category:** ALGORITHM (expected — structural baseline by design)
**Cause:** `SUPPRESS_RETURN_CODE_CHECK` and `ALTER_ERROR_BRANCH` both alter `COND=` parameter values without changing job step topology. Structural dependency analysis (Baseline-A) cannot detect changes to conditional guards because it only models which steps depend on which datasets/programs, not the threshold values of those dependencies.
**Evidence:** `results/rq2/rq2.csv`: fn_structural=1 for all 8 SUPPRESS_RETURN_CODE_CHECK mutations and all 8 ALTER_ERROR_BRANCH mutations across 2 files (CREADB21.jcl, TRANEXTR.jcl). Total: 16/19 Baseline-A FNs come from these two operators.
**Impact:** This is the primary discriminating finding for RELIC's contribution. BCGDiff correctly detects all 8+8=16 via confidence-delta mechanism. This is a FEATURE, not a failure — it validates the core claim that confidence-delta differencing catches behavioral weakening that structural analysis cannot see.
**Fixable:** N/A — this is a deliberate design outcome, not an error.
**Fixed:** N/A
**Residual Limitation:** The n=8 per operator is modest. Both operators are concentrated in 2 files from the transaction/batch domain. Generalization across all JCL file types is not demonstrated. Paper must note: "n=8 per operator (illustrative, domain-concentrated) — not sufficient for operator-level inferential claims."

## Failure: F-04 — RQ3 Dynamic Validation Is Simulation Circularity (Critical Limitation)

**Category:** METHODOLOGY
**Cause:** The 38 EXECUTION_SIMULATED traces are generated by parsing JCL step sequences — the same operation performed by the static contract extractor. The entity IDs in the traces (`step_entity.entity_id`) are generated by the same parser that constructs BCG nodes. Entity ID matching between trace events and BCG contracts is therefore guaranteed by construction, not by independent execution.
**Evidence:** `results/rq3/rq3_dynamic_results.json`: artifact_mapping.stats shows EXACT=0, MISSING=7,854 (all real GnuCOBOL trace events), PROC_EXPANDED=0. All 56 SUPPORTED promotions come from EXECUTION_SIMULATED traces (38 total). The 2 real EXECUTION traces (EMPPAY/DEPTPAY from public_cobol) contribute 0 promotions because their entity IDs do not match any JCL contract entity ID.
**Impact:** 91.8% dynamic validation rate is NOT independent corroboration. It measures internal consistency of the JCL parser with itself. The real execution validation rate is 0/61 = 0.0%. This is a CRITICAL framing issue: the paper cannot claim "execution-grounded" validation on RQ3.
**Fixable:** YES (framing-only fix, no new experiments needed). The simulation consistency result is still publishable if correctly framed as "JCL step-ordering simulation corroboration rate" rather than "dynamic execution validation."
**Fixed:** PARTIALLY — evidence_ledger.md correctly scopes this (entries RQ3-01 through RQ3-04). The fix must propagate to the paper's RQ3 framing, title, and abstract.
**Residual Limitation:** No genuine execution-grounding is available for JCL contracts without z/OS execution environment. GnuCOBOL traces corroborate only 2/61 contracts in the same system (different program domain). z/OS execution is blocked (external dependency).

## Failure: F-05 — One STATIC_DYNAMIC_CONFLICT in RQ3

**Category:** DATA_QUALITY
**Cause:** One contract was promoted to STATIC_DYNAMIC_CONFLICT, meaning a trace event was observed that contradicts the statically extracted contract. `rq3_dynamic_results.json` confirms 1 conflict exists. Per the paper's design, a conflict means either (a) the extractor produced a wrong contract or (b) the simulation trace incorrectly classified an event. Given the simulation circularity issue (F-04), the most likely cause is a trace ordering artifact in the JCL simulation, not a genuine extractor error.
**Evidence:** `results/rq3/rq3_dynamic_results.json`: contracts.STATIC_DYNAMIC_CONFLICT = 1.
**Impact:** Minimal — 1/61 = 1.6%. Does not change any metric meaningfully. The conflict rate is not reported as a headline metric.
**Fixable:** YES — could be investigated by inspecting the specific contract and trace. However, given F-04 simulation circularity, the conflict is likely a simulation artifact and resolving it would not add scientific value proportional to the effort.
**Fixed:** DOCUMENTED in FINAL_RESULTS.md (reported as STATIC_DYNAMIC_CONFLICT: 1, Rate: 1.6%).
**Residual Limitation:** The exact cause is not pinpointed. Paper footnote: "1/61 conflict (1.6%) — not investigated further given confirmed simulation circularity of trace source."

## Failure: F-07 — LLM Baselines Failed Due to API Rate Limit (Groq 100K TPD Quota)

**Category:** INFRASTRUCTURE
**Cause:** Groq free-tier TPD (tokens per day) quota = 100,000 tokens. 248 LLM calls × ~350 tokens/call ≈ 87,000 tokens. After 3–7 calls, quota was exhausted. HTTP 429 errors on remaining 245 (LLM-C) and 241 (LLM-D) calls. The code is correct; the infrastructure was insufficient.
**Evidence:** `results/rq2/llm_c_results.json`: n_errors=245, n_successful=3. LLM-C TP=2, FP=0, FN=102. LLM-D TP=6, FP=0, FN=98.
**Impact:** F1 values of 0.0377 (LLM-C) and 0.1091 (LLM-D) are lower bounds, not representative of LLM capability. Including them in a comparison table without this qualification would be scientifically misleading. The paper CANNOT claim "RELIC outperforms LLMs" based on these results.
**Fixable:** YES — requires paid Groq tier or locally-hosted model (Ollama, vLLM). Estimated cost: ~$0.50 per full run. NOT fixed in this sprint because it would require API credentials and potentially new experiments.
**Fixed:** DOCUMENTED as lower bounds in FINAL_RESULTS.md and evidence_ledger.md.
**Residual Limitation:** LLM comparison is not valid. Paper must either (a) exclude LLM baselines from main results table or (b) present them in a "preliminary investigation" section with explicit caveat that they represent infrastructure failure, not LLM capability.

## Failure: F-08 — PROC Reference Expansion Not Implemented (Parser Scope Limitation)

**Category:** PARSER_LIMITATION
**Cause:** The JCL parser (`src/legacy_contract/parsers/jcl_parser.py`) handles `PROC` and `PEND` tokens with a bare `pass` — inline and catalogued PROCedure expansion is not implemented. Three CardDemo JCL files reference `EXEC PROC=REPROC`: PRTCATBL.jcl, TRANBKP.jcl, TRANREPT.jcl.
**Evidence:** Grep of app/jcl directory finds 3 `EXEC PROC=REPROC` references. IF/THEN/ELSE/ENDIF: 0 files in CardDemo use modern conditional JCL syntax.
**Impact:** For the 3 files with PROC references, steps within the PROC are parsed as a single opaque step entity. Any contracts within the PROC body are not extracted. However, REPROC appears to be an inline PROC defined within the same JCL. RQ1 result shows TRANREPT.jcl has 1 contract detected by both oracle and extractor — suggesting the PROC reference does not prevent external step ordering contracts from being extracted.
**Fixable:** YES (technical limitation) — PROC expansion is a known future work item.
**Fixed:** DOCUMENTED in limitations.md (L10).
**Residual Limitation:** Systems that heavily use catalogued PROC libraries (typical in real enterprise mainframes) will have substantially more missed contracts than CardDemo. This must be in Threats to Validity.

## Failure: F-09 — N/A Rate 76.4% Creates Benchmark Selection Appearance

**Category:** BENCHMARK_DESIGN
**Cause:** 336/440 mutation attempts (76.4%) are classified N/A because: 208 files have zero valid contracts (single-step JCL), 126 operator-file combinations are inapplicable (e.g., CHANGE_DATASET_NAME on a file with no dataset dependencies), 2 produce no contract effect. The evaluated benchmark is effectively 23.6% of the attempted mutations.
**Evidence:** `results/rq2/rq2_summary.json`: n_not_applicable=336, n_evaluated_mutations=104. `results/FINAL_RESULTS_MANIFEST.json` forensic_audit_findings.rq2_na_taxonomy confirmed.
**Impact:** F1=1.000 is computed over the 104 evaluable cases, not the 440 attempts. Sensitivity analysis: worst-case (all N/A as FN) = F1=0.382; middle-case (zero-contract as FN) = F1=0.500. These three F1 values must all be reported in the paper.
**Fixable:** PARTIALLY — the N/A taxonomy is scientifically defensible (zero-contract files cannot be mutated; inapplicable operators genuinely do not apply). The fix is correct labeling and sensitivity reporting in the paper.
**Fixed:** Sensitivity analysis is in evidence_ledger.md. FINAL_RESULTS.md reports N=104 and N/A count.
**Residual Limitation:** A reader who sees F1=1.0 without the sensitivity analysis and N/A taxonomy will be misled. The paper must present all three F1 values with equal prominence.

## Failure: F-10 — OOD (public_cobol) Evaluation Has No Oracle

**Category:** BENCHMARK_DESIGN / ORACLE_LIMITATION
**Cause:** The public_cobol dataset (43 JCL files from Open Mainframe Project COBOL Programming Course) consists of pedagogical 1-2 step lab exercises. RELIC extracts 34 valid TEMPORAL contracts from these files, but no independent oracle exists to verify them. F1=0.0 is reported because there are 34 FP (unverifiable extracted contracts) and 0 TP.
**Evidence:** `docs/evidence_ledger.md` OOD-02 (CONFIRMED_LIMITATION): "OOD result F1=0.0 (tp=0, fp=34, fn=0) is a benchmark artifact, not extractor failure."
**Impact:** F1=0.0 on OOD is not interpretable as generalization failure. The 34 extracted contracts are structurally valid TEMPORAL contracts from multi-step JCL (the few that exist in public_cobol). Without an oracle, we cannot say whether RELIC is correct or wrong on this data.
**Fixable:** NO — requires independent oracle construction on public_cobol JCL, which requires qualified JCL annotators.
**Fixed:** DOCUMENTED.
**Residual Limitation:** Cross-system generalization cannot be evaluated with current public data. Paper must NOT present OOD F1=0.0 as evidence of failure. Must present it as "oracle unavailable — evaluation not possible."
