# Annotation Protocol (Final)
## LEGACY-CONTRACT — Level-3 Independent Ground Truth

**Document purpose:** Define the complete protocol for Level-3 independent human annotation
of behavioral contracts from JCL/COBOL artifacts.

**Scientific status:** This protocol governs the only evaluation pathway that can resolve
the RQ1 ground-truth circularity (C5). No automated result substitutes for this step.

**Date:** 2025

---

## 1. Why This Protocol Exists

The current Level-2 benchmark was generated by the extraction algorithm under evaluation.
F1 = 1.00 in that context is a mathematical identity (self-consistency check), not evidence
of correctness. To obtain an independent measurement of precision and recall, human annotators
must determine what behavioral contracts exist in the source artifacts without ever seeing:

- BCG extractor output
- Algorithm predictions
- Extracted contracts
- Confidence scores
- Expected answers
- Mutation labels generated by the system

This is a hard requirement. Any annotation that sees system output before forming a judgment
is contaminated and cannot serve as ground truth.

---

## 2. Ground Truth Hierarchy

### Level 1 — Execution Oracle (Highest)
When both original and modernized systems are executable: run both, collect traces,
compare behavior. Objective. Requires z/OS or equivalent execution environment.

### Level 2 — Deterministic Structural Facts (Current)
Facts mechanically verifiable from artifact grammar with no human judgment required.
Used as the current benchmark. **Circular for evaluating the same extractor family.**

### Level 3 — Independent Expert Annotation (This Protocol)
Contracts requiring semantic interpretation, annotated by domain experts who have not
seen the extraction algorithm's output. This is the target for non-circular evaluation.

### Level 4 — Researcher Adjudication
Resolution of Level-3 disagreements between annotators.

---

## 3. Annotator Qualifications

Qualified annotators must have:

- Demonstrated familiarity with JCL syntax (EXEC, DD, COND clauses)
- Familiarity with COBOL batch programming or equivalent mainframe batch experience
- No knowledge of or exposure to the BCG extraction algorithm, its implementation,
  or its outputs
- Willingness to follow the blinding protocol (see `annotation_blinding_protocol.md`)

A minimum of **two independent annotators** per item. Inter-annotator agreement
(Cohen's κ or Fleiss' κ) must be computed and reported before any evaluation.

Minimum acceptable κ: **0.60** (substantial agreement). Items below this threshold
in any contract type require adjudication before inclusion in the evaluation set.

---

## 4. What the Annotator Receives

For each item, the annotator receives:

1. **Artifact identifier** — the JCL filename (e.g., `CARDFILE.jcl`), no path
2. **Relevant source excerpt** — the specific lines of JCL or COBOL relevant to this item
3. **Surrounding context** — up to 20 lines before and after the excerpt, to preserve meaning
4. **Annotation instructions** — the task description (Section 5 of this document)
5. **Contract taxonomy** — the TEMPORAL / RESOURCE / CONTROL_FLOW taxonomy (Section 6)
6. **Candidate contract fields** — the annotation form schema (Section 7)

The annotator **does not receive**:

- The full file (to prevent anchor bias from reading surrounding unrelated content)
- Any extracted contract or prediction
- Any confidence score
- Any mention of what the system thinks about this excerpt
- The mutation label or any hint that a mutation was applied
- Any comparison with other annotators' responses (before adjudication)

---

## 5. Annotation Task Description

**Your task:** Examine the provided source excerpt from a JCL or COBOL artifact.
Determine whether the excerpt contains one or more behavioral contracts — explicit or
implicit obligations that must hold for the system to operate correctly.

A behavioral contract is an obligation of the form:
- "X must execute before Y"
- "X must produce resource R before Y consumes R"
- "If X returns code C, then Y must (or must not) execute"

For each potential contract you identify:
1. State whether a contract exists (yes / no / uncertain)
2. If yes: identify the contract type (TEMPORAL / RESOURCE / CONTROL_FLOW)
3. Identify the subject (the entity that has the obligation)
4. Identify the predicate (the nature of the obligation)
5. Identify the object (the entity or resource the obligation concerns)
6. Record the evidence span (exact text from the excerpt that justifies your judgment)
7. Rate your confidence (1 = low, 2 = medium, 3 = high)

You may find zero, one, or more contracts in a single excerpt.

---

## 6. Contract Taxonomy

### TEMPORAL
An obligation that one action must occur before another.

**Pattern:** "Step A must complete before Step B begins"

**JCL indicators:** Step ordering in the JCL (steps later in the file depend on steps
earlier), DISP=OLD/SHR on a dataset produced by a prior step, explicit dependency chains.

**Examples:**
- STEP010 must complete before STEP020 reads CUSTMAST
- CBACT01C must produce ACCTFILE before CBACT02C reads it

### RESOURCE
An obligation that a resource must be available (allocated, initialized, populated)
before it is consumed.

**Pattern:** "Resource R must exist and be ready before consumer C accesses it"

**JCL indicators:** DD statements with DISP=(NEW,CATLG), DISP=(OLD,KEEP),
dataset creation followed by dataset reference in a later step.

### CONTROL_FLOW
An obligation governing execution based on return codes or conditions.

**Pattern:** "If step A returns code X, then step B must (or must not) execute"

**JCL indicators:** COND= parameters on EXEC statements, conditional step execution,
return-code checks.

---

## 7. Annotation Form Schema

Complete one form per potential contract identified.

```json
{
  "annotation_id": "<generated by annotation tool, do not fill>",
  "source_excerpt_id": "<provided with the item>",
  "artifact_id": "<JCL filename, e.g. CARDFILE.jcl>",
  "annotator_id": "<your anonymized ID, assigned by protocol coordinator>",
  "annotation_timestamp": "<ISO8601 timestamp>",

  "contract_exists": true | false | "uncertain",

  "if_contract_exists": {
    "contract_type": "TEMPORAL" | "RESOURCE" | "CONTROL_FLOW",
    "subject": "<the entity with the obligation — step name, program name, etc.>",
    "predicate": "<the obligation — MUST_PRECEDE, PRODUCES_BEFORE_CONSUMES, MUST_NOT_FOLLOW_ON_ERROR, etc.>",
    "object": "<the entity or resource the obligation concerns>",
    "evidence_span": "<exact text from excerpt that supports this judgment>",
    "confidence": 1 | 2 | 3
  },

  "notes": "<optional free text — reasoning, uncertainties, ambiguities>",
  "time_spent_minutes": "<approximate>",

  "uncertainty_flag": false | true,
  "uncertainty_reason": "<if uncertain: explain what is ambiguous>"
}
```

---

## 8. Adjudication Protocol

When two annotators disagree on an item (different `contract_exists` verdict or
different `contract_type`):

1. Neither annotator's response is discarded
2. A third qualified annotator (the adjudicator) reviews the item and both responses
   without knowing which response came from which annotator
3. The adjudicator renders a final judgment
4. The adjudicator's judgment is the ground truth for that item
5. The item is flagged as `adjudicated=true` in the benchmark

If κ < 0.60 for a contract type, that type's annotation is flagged as LOW_AGREEMENT
and reported separately. Do not suppress these results.

---

## 9. Sample Size

For initial Level-3 evaluation, annotate a minimum of:

- 50 TEMPORAL contract candidates
- 20 CONTROL_FLOW contract candidates
- 20 RESOURCE contract candidates (requires sourcing additional JCL with RESOURCE contracts)

Also annotate a negative set: 30 JCL excerpts that the annotator judges contain no
behavioral contract. These are required to compute FPR.

Total minimum: 120 items.

## 11. Timeline and Completion Criteria

The Level-3 evaluation is complete when:

1. Both annotators have independently completed all assigned items
2. Inter-annotator agreement has been computed (κ reported by contract type)
3. All items with κ < 0.60 have been adjudicated
4. Final benchmark is locked (`evaluation/benchmark.py lock()`)
5. `scripts/import_annotation_results.py` has been run to produce `level3_human.json`
6. RQ1 evaluation has been re-run against `level3_human.json`

Until all six criteria are met, RQ1 status is **BLOCKED_FOR_INDEPENDENT_VALIDATION**.
